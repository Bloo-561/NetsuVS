**Since Oct 23–24 this is done by script:** `tools/sprite_port/` (guide: `tools/sprite_port/README.md` on the PC) turns the drawings in `Fighting_Game_All_Sprites` into 2× sprites (pixel size 0.00275, 27.5 units per sprite px), animation timelines, fitted hitboxes, states and moves (Cecilia's new set, Leticia, Flan's new set, and the assists Mary / Adin / Eren / Harie — `claude/assists.md`). The manual procedure below is how it was done before (Cecilia's 5A–j.C and 4A, Oct 18) and still explains what the scripts produce. **Sprites were frozen on Oct 23** (see Status and `claude/sprites-start-here.md`); the Oct 24 ports used the finished art the user supplied.

**Physics units (corrected Oct 24):** the engine moves `position += velocity / 60` every frame (two physics half-steps of velocity / 120 each). Older notes here said "/ 120 per frame"; that was one half-step. Gravity: `velocity -= force / 60` every frame. The move preview tool (`movereel.py`) had the same mistake until Oct 24 (it showed moves at half speed); Leticia's tables were halved to match the previews she was tuned on.

## Safety rules
- Before replacing anything, copy the old files to `_backup_stage_select/pre_<move>/` (`.tres` saved as `.tres.bak`, `.cs` as `.cs.bak`), or next to the file as `.tres.bak_<reason>`. Deleting is only for files the user asks to delete.
- Never use the Mahou EOS credentials.
- Keep each `.tres`'s existing `uid` when regenerating it, so nothing that references it breaks.
- **Adding a reference to an existing `.tres`/`.tscn`:** new `[ext_resource ...]` lines go with the other ext_resources at the TOP, before the first `[sub_resource]` / `[node]` / `[resource]`. Godot refuses the file otherwise (Oct 20: four Luminous Divider state references were added just above `[resource]` in `0_CEC_Data.tres`, her data failed to load and battles crashed; fixed in another chat, backup `_backup_stage_select/pre_cec_data_fix/`). After editing, check that no ext_resource comes after the first sub_resource in any file.
- After deleting or moving files, scan every `.tres`/`.tscn` for `res://` paths that no longer exist (there should be 0): `tools/sprite_port/check_refs.py`.
- **State event lists:** write empty ones as `= null` (as Godot does) rather than leaving them out; a missing list used to crash the engine when the state ran (engine null-checks added Oct 24, `fdk.py` writes `= null` since then).

## Quality bar: no drift, no flicker (the user's standard, Oct 22–23)
ChatGPT redraws the whole character every frame, so details (leg ribbons, hilt diamonds, hair strands, face shape) change between frames and read as flicker; it also shifts the body a few px sideways and draws the floor at a different height in every frame. The user wants BlazBlue/UNI-clean loops at 60 fps. Method that worked (idle):
1. **Inspect every candidate** against the master frame: per-region drift (head/chest/hem, alpha+luma matching), side-by-side sheet, 4× crops of face, legs, hilt. Pick the version with the least drift; reject frames that redraw the pose. Check file format too (Oct 23: one ChatGPT result had two small figures on one canvas, another a baked-in checkerboard background and no alpha).
2. **Lock whatever doesn't need to move** to one master drawing. Idle v3 used ONLY `01_ready` for the whole body; idle v4 does the same with `5w1`.
3. **Make motion with warps, not redraws:** per-row vertical displacement (head full, chest 0.7, hem 0.25, fading to 0 at the thighs) gives breathing.
4. **Swap only the part that must change** (eyes for blinks): align, cut a feathered patch, composite on the master.
5. **New pose every 4–6 frames** for loops; reuse a drawing at several warp heights.
6. **Downscale** with premultiplied alpha + Lanczos, same scale/offset for every frame (no jitter).
7. **Verify by LOOKING at the motion**, not only by numbers: 4× crops and a GIF preview to the user before installing. Say honestly if it isn't at the bar yet.
8. **One style per fighter.** A frame drawn in another style (Oct 21–23: the 01_ready idle among the Oct 17–18 set) pops every time the animation changes, however clean it is on its own.

## Processing a sheet (manual way, pre-port)
1. **Split frames:** label connected pixels (alpha > 60, dilate 2). Frames joined by swords/trails: split with a higher alpha threshold (200–250) as seeds, or a hand-placed cut line. Check every cut visually. Drop pixels with alpha ≤ 60 (that's the red-orange fringe ChatGPT leaves) and make the rest fully opaque. Stray specks go to the frame whose centre is nearest (or flood-fill from the torso and drop everything not connected).
2. **Scale:** all frames from one sheet get one scale.
   - Standing: match 5A/5B height (~250 px on the 1024 canvas, ahoge included); headband ~19 px wide. Flan: ~242 px. 1049×1500 source art: scale 250/1433 = 0.1745.
   - Crouching: match the crouch sprite `duck2stand` (~190 px tall).
   - Air: match the jump sprites (`jump_n2`, ~195 px tall); headband ~18 px wide is a good cross-check.
3. **Place** on a 1024×1024 canvas, sprite Offset `Vector2(-496, -404)`:
   - Ground moves: rear foot (left edge of the bottom 30 rows) at x = 403 standing / 416 crouching; feet bottom at y = 620–621.
   - Air moves: centre of the body on the same point as `jump_n2`. Using the centroid of dark pixels (value < 0.35: jacket, hair, socks, outlines) works because blades and trails are bright.
   - **Offset direction:** raising Offset.y moves the sprite UP in game (Sprite3D is y-up: canvas row r sits at height offset.y + 1024 − r px, so row 620 = the floor at −404). To push a sprite down N px, use −404 − N.
   - **Lying on the floor:** `hurt_down_floor.png` (the lying sprite squashed to 82% height so it reads as flat on the ground) at Offset `(-496, -434)`, used by knockdown slide/roll, Hit_Down and KO. Make the same for each new fighter.
4. **Units:** 55 units per canvas pixel (old 1× sprites; the 2× port is 27.5). x = (px − 496) × 55, y = (620 − py) × 55.
5. **Lace/white detection:** near-white skin highlights are warm; lace and sheath are cool white/grey. Test `b >= r − 0.03` or skin gets classified as lace.

## Building the move
- **AnimationData:** one SpriteModifier + AnimationSettings(AtFrame) per frame; HitboxState list (stage 0 startup, 1 active, 2 recovery); AttackProfile P0 (BaseDamage, GuardCrushDamage, AKT_LVLn).
- **Hitboxes (HitboxSettings):** hurtboxes (default type), proximity guard (HitboxType 2), attack (HitboxType 1), projectile (3), counter (5). HitType 0 high (air moves), 1 mid, 2 low. Give each pose its own file. Add an arm hurtbox when a limb is extended (4A frames 2–3). Templates: `5_Hitbox_5A_0` (no attack) and `5_Hitbox_5A_2` (attack) for standing moves; `15_Hitbox_j_5C_*` for air moves.
- **One hit window** across art with two hit frames, so the move can't double-hit by accident (ask the user if they want multi-hit).
- **States/Moves:** a Move's `MoveState` is the state's POSITION in `0_<TAG>_Data.tres` → `States`, not the number in the file name. Retime the state's movement events (MoveX velocity, inertia ranges) when the frame timing changes.
- **State → animation:** check that the move's State points at the move's own AnimationData. Cecilia's j.C state played the 5C animation for a day before anyone noticed (Flan's j.C state still does).
- **Removing moves:** keep the `States` list the same length (point emptied slots at the idle state) so state numbers don't shift. Removing entries from a stance's `Moves` list DOES shift move numbers, so renumber every `CanCancelTo` MoveIndex. Then re-run the CPU build script and update `command_list.json`.
- **Charge moves:** the engine has button RELEASE detection (`InputManager.WasReleased`, `ButtonMode.RELEASE`), `CheckInputCondition`, `GoToFrameActions` and custom variables, so hold-to-charge moves (Cecilia's j.C) can be built in data.
- **Slash trails (only on contact):** cut trails out of the body sprite into `Sprites/fx/<sprite>_fx.png` (same 1024 canvas). A trail is a red/pink/white blob whose edge touches mostly empty space; white pixels next to the blade's dark outline stay with the blade; trail pixels on top of her body stay in the body. Where a trail hid a limb (2B/2C back leg) keep the trail inside the limb's convex outline so nothing floats on a whiff. In the AnimationData add a second SpriteModifier (same Offset, `OnlyOnContact = true`) to that frame's `Modifiers`. Skin scenes need the `FX` Sprite3D after `Sprite` (Cecilia's have it). Check with a whiff-vs-hit preview.
- **Smoothness:** aim for 2–3 game frames per drawing on motion frames (BlazBlue standard); loops 4–6 per pose. Single-drawing reactions can be given motion with SpriteModifier `Offset`/`Rotation` keys (rotation pivots on the ground point under her). Victims shake during hitstop and heavy hits shake the camera automatically (engine). Turn on `Afterimages` in an AnimationData for dashes/slides.
- **Walk speed / footsteps:** MoveX `Velocity` in the walk state (position += velocity / 60 per frame; Cecilia forward 32000 = 3.2 m/s, back −21000). Footstep sound: `AtFrameCondition` (Frame + Modulo on the state frame); a second footstep = a second FrameDataEvent reusing the same PlaySound action, added to `OnTickEvents`.
- **Specials (learned building Luminous Divider, Oct 20):**
  - Button checks in an input are AND (Buttons = 6 means B+C together). To accept either of two buttons, put both sequences in `ValidInputs` (`41_Input_214B_or_C.tres`).
  - Neutral move lookup runs from the END of the stance `Moves` list, first match wins; cancels run through `CanCancelTo` in order, first match wins. So put EX first, then distance-limited versions, then the plain ones, and list specials before normals in each normal's CanCancelTo (214A ends in A, which would also match 5A). A move with `SkipCheck = true` is never found from neutral.
  - "C without meter = B": the EX move has `SuperGaugeRequired`; if it fails, the B move (input B or C) matches next.
  - `MoveSettings.DistanceArea` picks a far version; `SuperFlash` freezes the opponent (and, since Oct 24, the opponent's assist).
  - Pass through the opponent: hitbox file without a `Pushbox` line. Invincible: no hurtboxes, plus `SetFramePropertiesAction` (1 damage, 2 throw immunity; reset it on exit). Multi-hit: `ResetHitAction`. Teleport behind on hit: `TeleportAction` in `OnHitConfirmEvents` (x relative to OPPONENT, -9000 = 0.9 m behind them). Facing: `ChangeSideAction` (not forced) turns her toward the opponent.
  - **A state played from `OnHitConfirmEvents` starts with the opponent already marked as hit** (the engine adds them after the events run): put a `ResetHitAction` on that state's first active frame, or its first hit can't land.
  - Hit reactions are indices into the stance `HitReactions` list: 0 weak, 1 strong, 2 crouch, 3 sweep, 4/5 air weak/strong, 6 crumple, 7 launch away, 8 launch up, 9 launch down, 10 ground bounce, 11 wall bounce, 14 knockdown. `GroundHitstunType` 3 = hard knockdown (no tech). Movement: position += velocity / 60 per frame.
- **Gatlings:** A > B > C chains are set in each Move's `CanCancelTo` (see the character doc). New normals must be added to those lists.
- **Check:** draw the hitboxes over the frames (red attack, green hurt, blue proximity) and look at them; send the user the preview + hitbox images.
